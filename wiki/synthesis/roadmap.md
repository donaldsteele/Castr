# Castr roadmap and milestone status

**Read this page first when resuming work on Castr after a session restart.** This is the durable, cross-session task list — in-session `TodoWrite` state does not persist, this page does. Update it at the close of every milestone (and whenever milestone status changes) before ending a session or compacting context, per [[castr-project]]'s stated resumability requirement.

Merged to `main`. |

## Definition of done (every milestone)

Per [[castr-project-plan]]: tests passing, a `/wiki:ingest` summary committed, `graphify --update` run if code changed, and a QA subagent pass (an independent `Agent` spawned to exercise/review the milestone's tests and behavior) before moving to the next milestone.

## Open items carried forward

- **🔴 ACTIVE: M6 improved average throughput but not consistency — a bursty burst/stall delivery pattern remains, and the investigation has identified a self-inflicted congestion loop** (new, 2026-07-25, post-M6 user field report: ~8 MB/s but visibly bursting then stalling). Two independent agents (systems-design + a UFTP reference contrast) converged on the same primary cause, then a **91-run instrumented measurement campaign** measured it directly. Full write-up in `docs/METHODOLOGY.md`; all numbers in `docs/benchmarks/throughput-runs.md`.
  - **STATUS: P0, P1 and P2 are implemented in an isolated worktree but NOT MERGED** — see [[m7-repair-amplification]]. Round 1 of review returned **QA FAIL** (a reproduced liveness hang: the carousel-idle valve used one global timer refreshed by any chunk-bearing datagram, and since repair responses are multicast, any peer's repair traffic — or a replay of an already-held chunk — held every receiver's valve shut forever) plus **systems-design MERGE-WITH-CHANGES**. Round 2 fixed the hang (valve now keyed on that file's watermark advancing from a carousel delivery, per file), added the per-pass request cap that actually bounds amplification, and replaced an inert pass-counting jitter with per-chunk wall-clock jitter. **Retained claims: wire amplification 2.39× → 1.13×, duplicate chunk transmissions −99.7%, PEER_HAVE fragment gossip 20,557 → 68 datagrams, and the periodic stall eliminated. The "+112.6% goodput" claim was WITHDRAWN** — it was recovery from a degraded host state (that run set's own baseline was 2.8× below the documented warm baseline). **Net goodput effect remains unresolved** and the campaign's −11% warning below is *not* refuted. P3–P6 remain unimplemented.
  - **⚠️ MEASURED RE-RANKING — the derived priority order below was wrong.** The boring parameter change beats the elegant protocol fixes: **chunk 256K alone is +77%**, and **chunk 256K + datagram 60000 reaches 0.81 s / 98.6 MB/s (7.2× baseline) at *lower* wire amplification (1.82×) than today's 2.52×**. So **P5 and P4 are now the top-ranked work, not P0/P1.** Retain P0/P1/P2 for correctness and scaling reasons, but expect the throughput to come from chunk/datagram sizing.
  - **⚠️ P0 cannot be fixed in isolation.** Disabling premature repair *alone* measured **11% slower** (6.60 s vs 5.86 s; the carousel itself slowed 4.76 → 6.60 s), because `HandleChunkRequestAsync` runs concurrently with the carousel and the redundant repair stream is currently **the only thing giving the sender send-path parallelism**. The waste is accidentally load-bearing — the same trap M6 round 1 hit from the other direction. Pair any amplification fix with real send batching.
  - **Measured facts that revise the analysis below:** the stall period is **5.10 s** (`RepairOptions.RequestTimeout`), not 250 ms — only 4 of ~65 repair passes ever emit a request. Amplitude is **0.00 → 39 MB/s**, with up to **70% of a transfer in total dead air** at window 4. The first repair request asks for **10,212 of 10,240 chunks** while the carousel is ~1% done, so **the file is sent twice** (2.52× amplification, zero actual loss). **Both sides are bound by per-datagram cost (~32 µs each way)**, not bytes or crypto — `SendToAsync` is 66% of sender CPU; GC is not a factor. **The sender drops 87–97.5% of datagrams offered to its own socket**, so receivers' `CHUNK_REQUEST`/`JOIN_REQUEST` are dropped at the sender with **>90% probability during the carousel** (P2 is a correctness hazard, not just waste). **`SO_RCVBUF` is granted in full — no clamping.** **Receiver-side loss is entirely self-inflicted:** 0% with repair off, 12% at baseline, 48.8% at window 4.
  - **Methodology finding that invalidates part of M6's data:** the **OS page cache is a ~2× confounder** (12.6 s cold vs 6.5 s warm on identical config and identical datagram counts). **M6 round 2's "consistent 1.4–1.6× win at window 2" did not reproduce** — warm/interleaved/n=3 gives window 2 = **−13%** and window 4 = **−63%**. Keeping `DefaultSendWindowSize = 1` is vindicated, and the open item below about raising it should be considered **closed against raising it** pending genuinely new cross-machine evidence. Also `netstat -s -p udp` "Receive Errors" reads **0** despite 200k–370k dropped datagrams — unusable on Windows.
  - **Pre-existing test flaw — FIXED in the M7 worktree:** `UdpMulticastTransportTests` bound **hardcoded UDP ports** and failed with `WSAEACCES` when a system process held one (root cause confirmed: `DnsService` holds UDP 46101 on this host). Now asks the OS for a bindable ephemeral port via a `FreeUdpPort()` helper; the tests still bind real sockets and assert real delivery.
  - **New wire-format fact worth keeping (established during M7 review):** a **new message type is additively backward-compatible** — an unknown tag throws in `MessageCodec.Decode` and both sessions already swallow that — but **appending a field to an existing message type is NOT**: a new reader hits end-of-span on an old message and throws. So the eventual `ChunkRequestMessage` target field (needed for repair-response deduplication) must be a new type or a format-version bump, not an append.
  - Derived ranking as originally recorded, retained for the mechanisms (magnitudes now superseded above; P0/P1/P2 implementation status is in [[m7-repair-amplification]]):
  - **P0 — repair storm (no wire change needed).** `ReceiveRunner.RunRepairLoopAsync` polls every 250 ms unconditionally; at the first tick `ReceiverSession.RequestRepairsAsync` lists *every* not-yet-arrived chunk (~9,900 of 10,240 for an 80 MiB transfer) with no cap and no notion of what the carousel has actually sent, `RepairCoordinator.PlanRepairs` puts them all in one ~35-fragment all-or-nothing request, and `SenderSession.HandleChunkRequestAsync` re-reads/re-encrypts/re-proofs and re-sends all of them **concurrently with the still-running carousel**. Roughly doubles wire bytes and sender CPU. Worse, `_pending` is marked *before* the request is sent and `RepairOptions.RequestTimeout` is 5 s, so losing one request fragment (likely — it's injected into the congestion it's trying to fix) costs a full 5 s of silence. **The real stall quantum is ~5 s, not 250 ms.** Fix: cap requests to one datagram, add a carousel watermark, mark `_pending` after a successful send, add the jitter/backoff that [[repair-protocol]] already claims, and get `HandleChunkRequestAsync` off the sender's incoming loop.
  - **P1 — `PEER_HAVE` is quadratic in file size (no wire change needed).** `ReceiverSession.HandleChunkAsync` broadcasts the *entire* bitmap on every verified chunk, as an awaited socket send **inside `_stateGate`**. Total gossip = `FileSize² / (8 · chunkSize²)`: ~13.6 MB for 80 MiB at 8 KB chunks (15% of all datagrams), **~1.31 GB for an 800 MiB file — more than the payload.** Fix: coalesce to a section/time boundary and snapshot-then-send outside the gate. Peer discovery (the dual purpose noted in [[wire-protocol]]) is fully preserved. Note this cost was already visible in M6's own chunk-8192→60000 measurement and was misattributed to datagram count at the time.
  - **P2 — the sender receives and decodes its own entire transmission (~5-line fix).** `UdpMulticastTransport` always `AddMembership` + `MulticastLoopback=true` for both roles, and `SenderSession` has no own-echo filter (unlike `ReceiverSession`, which filters its own `PEER_HAVE` and its own `CHUNK_REQUEST`). All ~133,120 of its own chunk datagrams loop back, get fully `MessageCodec.Decode`d, and are dropped — starving its own 4 MB buffer and 4096-slot inbox so the kernel drops **real `CHUNK_REQUEST`/`JOIN_REQUEST` control traffic.** Fix: pre-decode message-type filter on `datagram[1]`.
  - **P3 — `_stateGate` is taken per *datagram* (13× per chunk), holding a disk write and two socket sends.** ~30,720 serialized awaited I/O ops per transfer. Crypto is not the cost (~8 µs/chunk); the I/O placement is.
  - **P4 — `ChunkPacketizer.Split` sizes every packet against packet 0's proof**, so 12 of 13 packets carry 728 bytes in a 1200-byte budget (39% waste) — 13 datagrams/chunk instead of 8. The in-code comment calls this "a few spare bytes," which was true when proofs were small and degrades with chunk count. **Requires sender+receiver lockstep** (`ChunkPacketAssembler` rejects mismatched slicing metadata), though no field layout changes. Also: `maxDatagramPayloadBytes` is threaded through both sessions but **exposed by no CLI or GUI surface** — always the 1200 default.
  - **P5 — `CastrPaths.DefaultChunkSize = 8192` contradicts the documented 256 KB–1 MB range in the same file that cites it.** Chunk size is the multiplier on P0, P1 and P3. Raise *after* P0 so the gain is attributable and coarser repair granularity is exercised against a healthy repair path.
  - **P6 — `_chunkCache` never evicts** (writes at `ReceiverSession.cs:352`, no `Remove` anywhere) — ~100 MB live set plus ~143k small objects for an 80 MiB transfer, guaranteeing gen2 GC pauses *during* the transfer. An independent contributor to rate inconsistency. M6 round 3 flagged the bounded channel as a memory surface and missed this, which is ~25× larger and unbounded in transfer size.
  - **Rejected, with reasons:** porting UFTP's TFMCC congestion control (UFTP's default rate is 1000 Kbps — *slower* than Castr; its wire-speed mode is unpaced exactly like Castr, and its own `cc_type` default is `none`, so this is not the source of its advantage), and adopting UFTP's group-HMAC data-path integrity (Castr's Merkle-over-ciphertext is what makes untrusted-peer repair safe — it is the load-bearing primitive for the whole swarm and mobile tier, and the per-chunk cost should be amortized with bigger chunks, not traded away).
  - **Also open, non-throughput:** `Castr.Tui.TransferDashboard`'s `new SemaphoreSlim(0)` has no max count, so its `SemaphoreFullException` catch is dead code and permits accumulate one-per-progress-event — the render loop never actually waits and re-renders unthrottled. TUI/GUI only (the CLI path is percent-bucketed). One-line fix: `new SemaphoreSlim(0, 1)`.
- **🟡 TRACKED FOLLOW-UP: run the `{P0, P0+w2, P0+w4}` send-window matrix on a host that reproduces the 13.65 MB/s baseline.** Owned outcome of the M7 review (see [[m7-repair-amplification]]). **Why it matters:** the 91-run campaign measured that removing premature repair costs **−11%**, because `HandleChunkRequestAsync` running concurrently with `RunChunkCarouselAsync` is currently the *only* thing giving the sender send-path parallelism — and M7 removes exactly that traffic (duplicate chunk datagrams −99.7%). M7's own A/B could not settle whether that regression materialises, because it ran on a degraded host whose baseline was 2.8× low. A send window >1 is the obvious candidate for restoring the parallelism deliberately rather than as a side effect of waste, so this matrix is what would either recover the ≤11% goodput risk or confirm it is real. Note this is *not* a licence to raise `DefaultSendWindowSize` — that remains a separate, independently-gated decision (see the item below); this is a measurement task. Prerequisite: a host reproducing the documented warm baseline, since that is precisely what M7's numbers lacked.
- **Formal release automation (tag-triggered `release.yml`, checksums/signatures, GitHub Release notes) has not been started** — this was the *original* scope of M5 in [[castr-project-plan]]; this session redirected the M5 slot to the showcase-docs work instead (see above), so release automation is carried forward here rather than dropped silently. `ci.yml`'s existing `package` job (from [[m3-test-ci-hardening-summary]]) already produces unsigned per-RID zips on every `main` push, which is a running start but not a tagged/checksummed/signed release.
- **M6's `SenderSession.DefaultSendWindowSize` stays at 1 (a no-op) despite consistent round-2/round-3 data suggesting 2 is now a real win** — see [[m6-throughput-pipelining]] and `SenderSession.DefaultSendWindowSize`'s XML doc for the full trial-by-trial numbers across all three rounds, both independently confirmed by a second reviewer in round 3. The default was deliberately kept at 1 anyway: all validation to date is single-machine/loopback-only, and round 1's initial default was already wrong once under exactly this kind of self-run benchmark. **Next step for whoever picks this up**: independent, cross-machine, real-LAN validation (ideally by someone who didn't write the round-2/3 benchmarks) is the stated bar for bumping the shipped default to 2 — `castr send --send-window-size 2` is available today for anyone who wants to opt in ahead of that.
- **A shared-gate fix for M6's independent-per-loop window double-counting was prototyped and reverted** (from M6 round 2, re-confirmed as an acceptable tradeoff in round 3) — `RunChunkCarouselAsync` and `HandleChunkRequestAsync` each independently cap concurrency at `sendWindowSize`, so simultaneous heavy repair traffic during an in-flight carousel can transiently push real concurrent sends to 2x the configured window (4, at a hypothetical default of 2); a shared `SemaphoreSlim` gate across both loops closes this but cost a measured, reproducible ~30% real-socket throughput regression even with zero actual contention in the benchmark — not worth it for a narrow, non-blocking correctness gap that's currently capped at a validated-safe spike of 2 (since the default is 1). Documented in-code (`SenderSession._sendWindowSize`'s field comment) with an explicit note that this gap must be re-validated before the default, or any recommended `--send-window-size` value, is raised above 1.
- **`Castr.Core.Discovery`'s mobile swarm-pull transport (`UdpUnicastTransport`/TCP framing) was not touched by M6** — it plausibly has the same synchronous receive-then-process architectural shape the multicast tier had before M6's fix, per systems-design's round-3 review, but this wasn't independently verified and no fix was attempted; carried forward as a real, likely-latent gap for a future pass.
- **`SwarmServeListener` accumulates connection-handler tasks without pruning** (new, from M4 QA — see [[m4-mobile-summary]]) — `RunAsync` adds every accepted connection's handler `Task` to a list and only awaits/prunes at cancellation, so a serve loop living across many mobile pull/reconnect cycles slowly leaks completed-but-retained `Task` references, with no cap on concurrent handlers either. Not a crash, not security-relevant (each handler's own allocations stay bounded) — worth fixing before a sender is expected to serve many mobile pullers over a long-lived session.
- **iOS `MobileReceiveViewModel` can't cancel an in-flight pull and doesn't cancel its `CancellationTokenSource` on dispose** (new, from M4 QA — see [[m4-mobile-summary]]) — unlike the Android `SwarmReceiveViewModel`, which has a working `CancelPull` command. UX/robustness gap only; a benign teardown race disposing the session's pull-gate semaphore mid-pull exists on both but is swallowed by each `PullAsync`'s catch-all.
- **iOS Simulator build blocked by an upstream libsodium packaging gap** (new, from M4 — see [[m4-mobile-summary]]) — `NSec.Cryptography` pins `libsodium` to `[1.0.22, 1.0.23)`, and that version ships no `iossimulator-arm64` (or any iOS Simulator RID) native slice at all, confirmed by inspecting the NuGet package's `runtimes/` folder directly. `ld` correctly refuses to link the device-platform `libsodium.a` into a simulator binary. `Castr.Core.Discovery`'s net10.0-ios head (the real NWBrowser/NWListener bindings) compiles and links fine on real Xcode CI — only the full `Castr.Gui.iOS` app-level link is blocked. Not fixable in Castr's code; needs either an NSec/libsodium release with simulator slices, or moving this CI leg to a signed real-device build (reintroducing the code-signing complexity deliberately deferred to M5). `ci-mobile-ios.yml` documents this inline and tolerates it via `continue-on-error` so CI still gates on what's real.
- **`SwarmReceiveViewModel` and `MobileReceiveViewModel` are two independently-designed implementations of the same mobile-receive concept** (new, from M4 — see [[m4-mobile-summary]]) — the Android head (`Castr.Gui.Android`) uses `SwarmReceiveViewModel`, the iOS head (`Castr.Gui.iOS`) uses `MobileReceiveViewModel`; both live in the shared `Castr.Gui` library, both compile, both are covered by their own test file, and both work, but they diverged during two independent build efforts that never converged on one shared design. Worth unifying deliberately in a future pass rather than as a rushed CI fix — see [[m4-mobile-summary]] for the QA assessment of real risk/divergence between them.
- **Hands-on mobile discovery interop still not device/emulator-validated** (deferred from [[adr-0002-mobile-discovery]], narrowed by M4) — the *code* (`NsdManager`/`NWBrowser` bindings) is now implemented **and CI-verified to actually compile/link against each platform's real SDK/Xcode toolchain** (M4), which is a real step up from the M0-era spike, but genuine Android↔iOS mDNS interop over a real LAN, on a real device or emulator, still hasn't been exercised — no device/emulator or macOS host exists on the dev machine. **The Android 13+ runtime-permission question is resolved (M4 research):** `NsdManager` service discovery does **not** require `NEARBY_WIFI_DEVICES` — that permission gates only Wi-Fi Direct/Aware/RTT/LocalOnlyHotspot, not NSD. NSD needs only the install-time `INTERNET` + `ACCESS_WIFI_STATE` + `ACCESS_NETWORK_STATE`, and `Castr.Gui.Android`'s manifest is wired accordingly. (Forward-looking: Android 17+ `ACCESS_LOCAL_NETWORK` will gate `.local` resolution, but NsdManager is exempt during the Android 16 opt-in.)
- **Repeating carousel rounds and NACK-suppressed unicast-targeted repair** (new, from M1 — documented scope trims in [[m1-core-summary]]) — both are natural low-risk extensions to `SenderSession`/`ReceiverSession`, not required for correctness, worth revisiting opportunistically rather than blocking on them now.
- **Manifest metadata (file names/sizes) remains unencrypted** now that M1.5 has landed — [[adr-0003-payload-encryption]] only encrypts chunk payloads by design. Revisit if a deployment needs filename/metadata confidentiality too; documented as a known, deliberate scope boundary, not an oversight.
- **Sender-side receiver allowlist** is a plausible future hardening noted in [[adr-0003-payload-encryption]] but not required now — currently any receiver that completes `JOIN_REQUEST` (i.e. already trusts the sender's signature) gets the content key, matching today's receiver-side-only authorization model.
- **Session-ID uniqueness is a caller contract, not yet enforced in `Castr.Core`** (new, from M1.5 QA — see [[m1.5-encryption-summary]]) — `ContentKeyWrap`'s HKDF salt is the transfer's session ID, so a caller reusing one across transfers between the same sender/receiver pair risks wrap-key reuse. `Castr.Cli` generates a fresh random session ID per invocation, so this is currently safe in practice, but `Castr.Core` still doesn't enforce it itself.
- **`Castr.Tui`'s heatmap/throughput views are approximations** (new, from M2 — see [[m2-ui-summary]]) — `TransferProgress` only exposes aggregate counts, not the raw `ChunkBitmap` or per-peer byte counts, so the live dashboard shows completion density and aggregate MB/s rather than exact per-chunk/per-peer detail. Revisit if a richer Core progress API is ever justified.
- **`Castr.Gui.Tests` is the only xUnit v3 project in the repo** (new, from M2 — see [[m2-ui-summary]]) — required by `Avalonia.Headless.XUnit`; QA confirmed it coexists cleanly with the rest of the solution's xUnit v2 projects (no double-counting, no version conflicts) but it's worth knowing about before adding more test infra.
- **Replay protection's `issued-at` freshness window is not implemented** (confirmed, from M3's security test pass — see [[wire-protocol]] and [[m3-test-ci-hardening-summary]]) — `ReceiverSession` never inspects it against the clock, and `ANNOUNCE` is currently ignored entirely. Low severity (trust is keyed to sender fingerprint, not session/timestamp) but a real, confirmed gap, not just a documentation lag — revisit if session-replay risk is ever reassessed.
- **Large/multi-file manifests are more loss-fragile since M3's packetization** (see [[m3-test-ci-hardening-summary]]) — a manifest between ~1200 bytes and 64 KB now splits across multiple `PacketFragment` datagrams; losing any one still stalls a receiver, since there's no manifest re-request path (the same M1 scope trim as above, now amplified from one losable datagram to N). Natural candidate to fix alongside the repeating-carousel/NACK-suppression item above.
- **Reassembly eviction is FIFO-by-creation, not true LRU** despite the docstring (`PacketReassembler`/`ChunkPacketAssembler`, found during M3 QA) — never triggered in any shipped scenario and correctness holds even if it did, but the naming should be corrected if this code is touched again.
- **E2E `tc netem` loss concentrates on each chunk's packet-0** (found during M3's combined QA — see [[m3-test-ci-hardening-summary]]) — the loss filter's matched datagram-size window only reliably catches the Merkle-proof-carrying first packet of each chunk, not every packet; the test still validly exercises repair (losing packet 0 strands the chunk) but at a lower effective rate than the nominal percentage. Worth tightening if E2E loss-rate precision ever matters.
