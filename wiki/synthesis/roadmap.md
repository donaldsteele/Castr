# Castr roadmap and milestone status

**Read this page first when resuming work on Castr after a session restart.** This is the durable, cross-session task list — in-session `TodoWrite` state does not persist, this page does. Update it at the close of every milestone (and whenever milestone status changes) before ending a session or compacting context, per [[castr-project]]'s stated resumability requirement.

## Milestone status

| Milestone | Scope | Status |
|---|---|---|
| M0 — Scaffolding & spikes | Repo init, solution/project skeleton, LICENSE/.gitignore, `/wiki:init`, Ed25519 spike, mDNS/Info.plist spike | **Nearly done.** Repo initialized (git, Apache-2.0 LICENSE, .gitignore). Solution scaffolded: `Castr.Core`, `Castr.Core.Discovery`, `Castr.Cli`, `Castr.Tui` + matching test projects (`Castr.Core.Tests`, `Castr.Core.IntegrationTests`, `Castr.Core.E2ETests`, `Castr.Cli.Tests`) all build and the default scaffolded tests pass. Basic `ci.yml` (build+test matrix across ubuntu/windows/macos) added. `Castr.Gui*` intentionally left unscaffolded — see `src/Castr.Gui/PLACEHOLDER.md` — until M2/M4. `wiki/` initialized and this plan ingested as the first source. **Both M0 spikes complete**: see [[adr-0001-ed25519-library]] (NSec.Cryptography chosen; solution retargeted net8.0 → **net10.0 LTS** as a consequence, .NET 10 SDK installed) and [[adr-0002-mobile-discovery]] (native NsdManager/NWBrowser confirmed usable directly from C#, iOS Info.plist requirements documented). **M0 complete.** Initial commit pushed to `github.com:donaldsteele/Castr` on `main` (SSH auth configured via a dedicated ed25519 key for this machine, added to the user's GitHub account). QA subagent review of the full M0 scaffold found no defects (build/tests, project reference graph, git hygiene, LICENSE, wiki consistency, ADR fact-checks, CI workflow, GUI placeholder honesty — all verified independently, not just read).
| M1 — Castr.Core | Protocol state machines, chunker+Merkle/BLAKE3, manifest sign/verify, trust store+policy, path-safety, transport abstraction (real UDP + in-memory), `IPeerTable`/`RepairCoordinator`, full unit + loopback-multicast integration suite | **Complete, including QA fix.** See [[m1-core-summary]] for full detail. 167 unit tests (`Castr.Core.Tests`) + 4 real-socket integration tests (`Castr.Core.IntegrationTests`), all passing, verified stable across repeated runs. End-to-end `SenderSession`/`ReceiverSession` proven correct: happy path, 5-receiver fan-out from one send, untrusted-sender rejection, tampered-chunk detection + repair recovery, peer-served repair, and real-UDP-socket repair under 15% induced loss. QA subagent review attempted to break path safety / Merkle verification / signature checks (no bypass found) and did find + we fixed one real defect: a `UInt16` length-prefix overflow in `ChunkRequestMessage` encoding for repair batches over 65,535 chunks (realistic for large cold-start bulk repairs), widened to `UInt32`. Documented scope trims: single-pass carousel (no repeating rounds), repair request/response are multicast-broadcast rather than unicast-targeted with no NACK suppression. **Open risk carried to M3**: CI multicast behavior on GitHub-hosted runners is unverified — only confirmed working on this local Windows dev machine so far. |
| M1.5 — Payload encryption retrofit | X25519 keypairs, `JOIN_REQUEST`/`KEY_GRANT` handshake, ChaCha20-Poly1305 chunk encryption, Merkle-over-ciphertext, updated `SenderSession`/`ReceiverSession`, new tests | **Complete, including QA review.** See [[m1.5-encryption-summary]] for full detail. 186 unit tests (`Castr.Core.Tests`, up from 167) + 4 real-socket integration tests (`Castr.Core.IntegrationTests`), all passing. QA subagent independently rebuilt/re-ran the suite and actively verified tamper rejection, cross-context AAD rejection, per-file nonce uniqueness, MITM-proof manifest binding, and that the new handshake cannot bypass TOFU — no defects found. Two deliberate, QA-accepted deviations from the original wording in [[wire-protocol]]: `JOIN_REQUEST`/`KEY_GRANT` travel over the shared multicast channel (not a separate unicast socket), and the content key is generated outside `SenderSession`'s constructor and injected. `Castr.Core` now sends ciphertext-only chunk payloads. |
| M2 — CLI, TUI, Desktop GUI (parallel) | `Castr.Cli`, `Castr.Tui`, `Castr.Gui.Desktop`, each with its own test suite | **Complete, including QA review (PASS-WITH-CONCERNS).** See [[m2-ui-summary]] for full detail. Added a new `Castr.Core` observability contract first (`TransferProgress`/`ProgressChanged` events, `ITrustPrompt` interactive callback closing the previously-inert `TrustOutcome.PromptRequired` path) — QA'd separately before the three UI surfaces were built against it, no defects found. Then built in parallel: `Castr.Tui` (Spectre.Console `TransferDashboard`, library consumed by Cli), `Castr.Gui`/`Castr.Gui.Desktop` (newly scaffolded Avalonia MVVM app, verified via `Avalonia.Headless`), and `Castr.Cli` (System.CommandLine `send`/`receive`/`trust` commands, real loopback transfer personally verified). Full solution: 244 tests passing (Core 191, Cli 25, Tui 16, Gui 7, IntegrationTests 4, E2E 1), 0 warnings. QA's one non-blocking finding — a pre-existing M1 transport gap where large chunk sizes crash the sender and silently hang the receiver over real UDP (the documented chunk/wire-packet split was never implemented) — was mitigated with a `Castr.Cli` fail-fast `--chunk-size` guard rather than blocking M2 on a full Core fix; the underlying fix is tracked below and in [[wire-protocol]]. |
| M3 — Test/CI hardening | Full GitHub Actions matrix, Testcontainers E2E fan-out, security test pass (traversal/tamper/replay), `/wiki:lint` | **Complete, including two rounds of QA.** See [[m3-test-ci-hardening-summary]] for full detail. Closed the M2-carried transport gap (real two-level chunk/wire-packet split, `ChunkPacketizer`/`ChunkPacketAssembler` + `WirePacketizer`/`PacketReassembler`), built a real Testcontainers multi-container E2E fan-out suite (real `tc netem`-induced kernel loss, byte-identical recovery via repair), added 11 security tests (traversal/tamper/trust-store/TOFU-bypass), fixed a long-flaky `Castr.Tui.Tests` timing test, and — the milestone's biggest find — discovered and fixed CI's `macos-latest` leg had been silently failing since M1 (missing `IP_MULTICAST_IF` on macOS), verified green on real GitHub Actions runs via the newly-installed `gh` CLI, plus added a separate Docker-gated `e2e-docker` CI job. QA (dedicated review of the chunk/wire-packet split, then a combined review of the full M3 surface) found and fixed one should-fix defect (an unauthenticated reassembly memory-exhaustion DoS) and one incidental concurrency bug in `ReceiverSession` surfaced by the E2E suite's realistic load; final verdict PASS. 295 tests passing (Core 236, Cli 30, Tui 16, Gui 7, IntegrationTests 6) plus a separate opt-in E2E tier (3 tests), 0 warnings. **Follow-up after M3 closed**: `ci.yml` gained a `package` job (main-branch pushes only, gated on `build-and-test` + `e2e-docker` passing) that self-contained-publishes `Castr.Cli` and `Castr.Gui.Desktop` for five RIDs (win-x64, win-arm64, osx-x64, osx-arm64, linux-x64) from a single `ubuntu-latest` runner and uploads each as a downloadable zip workflow artifact — verified for real via a throwaway PR before merging to `main`. This is a CI convenience, not a release: builds are unsigned/unnotarized and there's no versioning/checksums/GitHub Release yet — that remains M5's scope (see below). |
| M4 — Mobile | `Castr.Core.Discovery` native mDNS impls, unicast swarm client, `Castr.Gui.Android`/`Castr.Gui.iOS`, sideload packaging | **Complete, including QA review (PASS-WITH-CONCERNS).** See [[m4-mobile-summary]] for full detail. New TCP unicast "swarm pull" tier in `Castr.Core` (`SwarmPullSession`/`SwarmServeListener`, length-prefixed framing, shared `ManifestAdmission` trust gate) alongside the existing multicast tier; real native mDNS (`NsdManager`/`NWBrowser`) in `Castr.Core.Discovery`; `Castr.Gui.Android` (real debug-signed APK, CI-verified) and `Castr.Gui.iOS` (real Xcode-linked `Castr.Core.Discovery` head, CI-verified) GUI heads. A real security defect was found and fixed *during* M4 in the core M1-era multicast path too, not just the new mobile code: `MerkleProof.Verify` didn't authenticate its own `LeafIndex` field against the proof's `Steps`, letting a malicious relaying peer relabel a genuine chunk's wire position and permanently stall a receiver — fixed by deriving `LeafIndex` from `Steps` inside the primitive itself. 359 tests passing, 0 warnings. QA found no security/trust/verification defects and confirmed the test/build numbers independently; two non-blocking findings (unbounded connection-task accumulation in `SwarmServeListener`, iOS view-model missing pull-cancellation) plus the already-known view-model duplication and iOS Simulator link gap are carried forward below. |
| M5 — Release automation & docs | Tag-triggered `release.yml`, self-contained per-RID publishes, checksums/signatures, GitHub Release notes, docs finalized | **In progress.** Docs-first slice done: `docs/SHOWCASE.md` — real, hands-on-captured GIFs/screenshots of `Castr.Cli`, `Castr.Tui`, and `Castr.Gui.Desktop` doing real loopback multicast transfers (LAN-party/sysadmin-fleet-push/test-lab framing), linked from a new README "See it in action" section. Captured via `ffmpeg`'s `ddagrab` (DXGI Desktop Duplication) — `gdigrab` was tried first and rejected: it desaturates Windows Terminal's GPU-composited rendering. Release automation itself (tag-triggered `release.yml`, checksums/signatures, GitHub Release notes) not yet started. Mobile (Android/iOS) has no showcase media — no emulator/Mac on the dev machine, tracked as a follow-up alongside the existing mobile hands-on-interop open item below. |
| M6 — Send-path throughput (perf) | Root-cause the ~1.6-2.4 MB/s demo-GIF plateau in `SenderSession`'s fully sequential send loop; implement bounded concurrent sends; re-measure | **Round 2 done (receiver-side fix + corrected default); QA/systems-design review of round 2 not yet done.** Round 1 shipped `Parallel.ForEachAsync`-based chunk-carousel/repair pipelining (safe against out-of-order UDP delivery — `PacketReassembler`/`ChunkPacketAssembler` are already fully index-keyed) with a `DefaultSendWindowSize = 2`. Independent QA + a systems-design review both rejected that default: QA re-measured it as a consistent ~1.8-2.7x *regression* vs. window=1 (round 1's smaller sample under-weighted this), and systems-design's code read pinpointed the real mechanism — `ReceiverSession.RunAsync`'s per-packet chain (Merkle/AEAD verify, disk write, PEER_HAVE broadcast) was fully serialized under one lock, and `UdpMulticastTransport.ReceiveAsync` had no decoupling from it, so the OS receive buffer only drained as fast as that whole chain ran; concurrent sending broke the old loop's accidental self-throttling and overwhelmed it. Round 2: (1) reverted the default to **1** (a true no-op — `RunAsync` already ran the carousel and repair listener as concurrent tasks pre-M6, so window=1 on each reproduces exactly that, no more); (2) fixed a `Castr.Tui.ThroughputSampler` data race (`Queue<T>` mutated without a lock from `ProgressChanged`, now routine under concurrent sends, not just rare) with a simple lock; (3) decoupled `UdpMulticastTransport`'s socket read from downstream processing — a dedicated reader task now drains the socket into a bounded `Channel<ReceivedPacket>` (`InboxCapacity = 4096`) independent of consumer speed; (4) set explicit 4 MB `SO_RCVBUF`/`SO_SNDBUF` (best-effort, matching `uftp-multicast`'s documented approach). **Re-benchmarked with the receiver-side fix in place, real two-process (`castr send`/`castr receive`) methodology throughout**: window=2 became a *consistent* ~1.4-1.6x win (no collapse, tight variance) in both a 1:1 transfer and a new 3-receiver fan-out benchmark with one receiver deliberately throttled to a single low-priority CPU core (repair-protocol.md's actual "one send, many receivers" case) — every receiver, including the throttled one, always finished byte-identical. window≥4 still gives the gain back (roughly to window=1's own throughput) but no longer catastrophically collapses like round 1's window≥3. Despite the encouraging data, the shipped default stays at **1**: a second good-looking number from the same benchmarking process isn't the same as an outside second opinion, per the coordinator's explicit instruction. Also added a `castr send --send-window-size` CLI flag (default 1) so a deployment that has validated a higher window for its own receiver hardware can opt in without a rebuild. Prototyped (then reverted) a shared-gate fix for a real but narrow correctness gap — independent per-loop `ParallelOptions` on the carousel and repair handler can transiently let real concurrent sends hit 2x the configured window during simultaneous heavy repair traffic — because a `SemaphoreSlim`-based shared gate measured a reproducible ~30% real-socket throughput cost even with zero contention, which was judged not worth paying for a narrow, non-blocking edge case; documented in-code as a known limitation instead. 363 tests passing (unchanged from round 1: 4 `SenderSessionPipeliningTests` plus everything else), including unmodified real-socket `ChaosTransport` loss/reorder/duplication integration tests, run repeatedly for stability. **Not done**: QA/systems-design review of round 2 itself (including the "should the default be 2" question the round-2 data reopens), and no receive-side change was made to `Castr.Core.Discovery`'s or the mobile swarm-pull tier's transports (out of this round's scope). |

## Definition of done (every milestone)

Per [[castr-project-plan]]: tests passing, a `/wiki:ingest` summary committed, `graphify --update` run if code changed, and a QA subagent pass (an independent `Agent` spawned to exercise/review the milestone's tests and behavior) before moving to the next milestone.

## Open items carried forward

- **M6's `SenderSession.DefaultSendWindowSize` stays at 1 (a no-op) despite round-2 data suggesting 2 is now a real, consistent win** (updated from M6 round 2 — see the M6 row above and `SenderSession.DefaultSendWindowSize`'s XML doc for the full three-round trial-by-trial numbers) — round 1 shipped 2, QA and systems-design both rejected it as measured-worse-than-characterized, and round 2's receiver-side fix (channel-decoupled `UdpMulticastTransport` read loop, explicit socket buffers) then measured window=2 as a consistent ~1.4-1.6x win with no collapse, including under a 3-receiver/one-throttled fan-out benchmark. The default was deliberately left at 1 anyway, per the coordinator's explicit instruction and the reasoning that one more good-looking self-run benchmark isn't the same as an outside second opinion after round 1's default was already wrong once. **Next step for whoever picks this up**: an independent QA/systems-design pass specifically on round 2's numbers and methodology (ideally on different hardware) is the blocker to bumping the shipped default to 2 — `castr send --send-window-size 2` is available today for anyone who wants to opt in ahead of that.
- **A shared-gate fix for M6's independent-per-loop window double-counting was prototyped and reverted** (new, from M6 round 2) — `RunChunkCarouselAsync` and `HandleChunkRequestAsync` each independently cap concurrency at `sendWindowSize`, so simultaneous heavy repair traffic during an in-flight carousel can transiently push real concurrent sends to 2x the configured window; a shared `SemaphoreSlim` gate across both loops closes this but cost a measured, reproducible ~30% real-socket throughput regression even with zero actual contention in the benchmark — not worth it for a narrow, non-blocking correctness gap. Documented in-code (`SenderSession._sendWindowSize`'s field comment) as a known limitation; worth revisiting with a cheaper gating primitive if the double-counting ever proves to matter in practice.
- **`SwarmServeListener` accumulates connection-handler tasks without pruning** (new, from M4 QA — see [[m4-mobile-summary]]) — `RunAsync` adds every accepted connection's handler `Task` to a list and only awaits/prunes at cancellation, so a serve loop living across many mobile pull/reconnect cycles slowly leaks completed-but-retained `Task` references, with no cap on concurrent handlers either. Not a crash, not security-relevant (each handler's own allocations stay bounded) — worth fixing before a sender is expected to serve many mobile pullers over a long-lived session.
- **iOS `MobileReceiveViewModel` can't cancel an in-flight pull and doesn't cancel its `CancellationTokenSource` on dispose** (new, from M4 QA — see [[m4-mobile-summary]]) — unlike the Android `SwarmReceiveViewModel`, which has a working `CancelPull` command. UX/robustness gap only; a benign teardown race disposing the session's pull-gate semaphore mid-pull exists on both but is swallowed by each `PullAsync`'s catch-all.
- **iOS Simulator build blocked by an upstream libsodium packaging gap** (new, from M4 — see [[m4-mobile-summary]]) — `NSec.Cryptography` pins `libsodium` to `[1.0.22, 1.0.23)`, and that version ships no `iossimulator-arm64` (or any iOS Simulator RID) native slice at all, confirmed by inspecting the NuGet package's `runtimes/` folder directly. `ld` correctly refuses to link the device-platform `libsodium.a` into a simulator binary. `Castr.Core.Discovery`'s net10.0-ios head (the real NWBrowser/NWListener bindings) compiles and links fine on real Xcode CI — only the full `Castr.Gui.iOS` app-level link is blocked. Not fixable in Castr's code; needs either an NSec/libsodium release with simulator slices, or moving this CI leg to a signed real-device build (reintroducing the code-signing complexity deliberately deferred to M5). `ci-mobile-ios.yml` documents this inline and tolerates it via `continue-on-error` so CI still gates on what's real.
- **`SwarmReceiveViewModel` and `MobileReceiveViewModel` are two independently-designed implementations of the same mobile-receive concept** (new, from M4 — see [[m4-mobile-summary]]) — the Android head (`Castr.Gui.Android`) uses `SwarmReceiveViewModel`, the iOS head (`Castr.Gui.iOS`) uses `MobileReceiveViewModel`; both live in the shared `Castr.Gui` library, both compile, both are covered by their own test file, and both work, but they diverged during two independent build efforts that never converged on one shared design. Worth unifying deliberately in a future pass rather than as a rushed CI fix — see [[m4-mobile-summary]] for the QA assessment of real risk/divergence between them.
- **Hands-on mobile discovery interop still not device/emulator-validated** (deferred from [[adr-0002-mobile-discovery]], narrowed by M4) — the *code* (`NsdManager`/`NWBrowser` bindings) is now implemented **and CI-verified to actually compile/link against each platform's real SDK/Xcode toolchain** (M4), which is a real step up from the M0-era spike, but genuine Android↔iOS mDNS interop over a real LAN, on a real device or emulator, still hasn't been exercised — no device/emulator or macOS host exists on the dev machine. **The Android 13+ runtime-permission question is resolved (M4 research):** `NsdManager` service discovery does **not** require `NEARBY_WIFI_DEVICES` — that permission gates only Wi-Fi Direct/Aware/RTT/LocalOnlyHotspot, not NSD. NSD needs only the install-time `INTERNET` + `ACCESS_WIFI_STATE` + `ACCESS_NETWORK_STATE`, and `Castr.Gui.Android`'s manifest is wired accordingly. (Forward-looking: Android 17+ `ACCESS_LOCAL_NETWORK` will gate `.local` resolution, but NsdManager is exempt during the Android 16 opt-in.)
- **Repeating carousel rounds and NACK-suppressed unicast-targeted repair** (new, from M1 — documented scope trims in [[m1-core-summary]]) — both are natural low-risk extensions to `SenderSession`/`ReceiverSession`, not required for correctness, worth revisiting opportunistically rather than blocking on them now.
- **Manifest metadata (file names/sizes) remains unencrypted** now that M1.5 has landed — [[adr-0003-payload-encryption]] only encrypts chunk payloads by design. Revisit if a deployment needs filename/metadata confidentiality too; documented as a known, deliberate scope boundary, not an oversight.
- **Sender-side receiver allowlist** is a plausible future hardening noted in [[adr-0003-payload-encryption]] but not required now — currently any receiver that completes `JOIN_REQUEST` (i.e. already trusts the sender's signature) gets the content key, matching today's receiver-side-only authorization model.
- **Session-ID uniqueness is a caller contract, not yet enforced in `Castr.Core`** (new, from M1.5 QA — see [[m1.5-encryption-summary]]) — `ContentKeyWrap`'s HKDF salt is the transfer's session ID, so a caller reusing one across transfers between the same sender/receiver pair risks wrap-key reuse. `Castr.Cli` generates a fresh random session ID per invocation, so this is currently safe in practice, but `Castr.Core` still doesn't enforce it itself.
- **`Castr.Tui`'s heatmap/throughput views are approximations** (new, from M2 — see [[m2-ui-summary]]) — `TransferProgress` only exposes aggregate counts, not the raw `ChunkBitmap` or per-peer byte counts, so the live dashboard shows completion density and aggregate MB/s rather than exact per-chunk/per-peer detail. Revisit if a richer Core progress API is ever justified.
- **`Castr.Gui.Tests` is the only xUnit v3 project in the repo** (new, from M2 — see [[m2-ui-summary]]) — required by `Avalonia.Headless.XUnit`; QA confirmed it coexists cleanly with the rest of the solution's xUnit v2 projects (no double-counting, no version conflicts) but it's worth knowing about before adding more test infra.
- **Replay protection's `issued-at` freshness window is not implemented** (confirmed, from M3's security test pass — see [[wire-protocol]] and [[m3-test-ci-hardening-summary]]) — `ReceiverSession` never inspects it against the clock, and `ANNOUNCE` is currently ignored entirely. Low severity (trust is keyed to sender fingerprint, not session/timestamp) but a real, confirmed gap, not just a documentation lag — revisit if session-replay risk is ever reassessed.
- **Large/multi-file manifests are more loss-fragile since M3's packetization** (see [[m3-test-ci-hardening-summary]]) — a manifest between ~1200 bytes and 64 KB now splits across multiple `PacketFragment` datagrams; losing any one still stalls a receiver, since there's no manifest re-request path (the same M1 scope trim as above, now amplified from one losable datagram to N). Natural candidate to fix alongside the repeating-carousel/NACK-suppression item above.
- **Reassembly eviction is FIFO-by-creation, not true LRU** despite the docstring (`PacketReassembler`/`ChunkPacketAssembler`, found during M3 QA) — never triggered in any shipped scenario and correctness holds even if it did, but the naming should be corrected if this code is touched again.
- **E2E `tc netem` loss concentrates on each chunk's packet-0** (found during M3's combined QA — see [[m3-test-ci-hardening-summary]]) — the loss filter's matched datagram-size window only reliably catches the Merkle-proof-carrying first packet of each chunk, not every packet; the test still validly exercises repair (losing packet 0 strands the chunk) but at a lower effective rate than the nominal percentage. Worth tightening if E2E loss-rate precision ever matters.
