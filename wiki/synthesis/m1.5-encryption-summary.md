# M1.5 — Payload encryption retrofit: implementation summary

M1.5 is complete: `Castr.Core` now encrypts every chunk payload, closing the gap documented in [[adr-0003-payload-encryption]] and superseding the plaintext behavior described in [[m1-core-summary]]. **186 unit tests** (`Castr.Core.Tests`, up from 167) and **4 real-socket integration tests** (`Castr.Core.IntegrationTests`) pass. M2 is unblocked.

## What was built

- **`Castr.Core.Security`**: `EncryptionKeys` (X25519 keypairs, separate from the existing Ed25519 identity keys), `ContentKey` (per-transfer 256-bit key; ChaCha20-Poly1305 chunk encrypt/decrypt with nonce = `(fileIndex, chunkIndex)` and AAD = `(sessionId, fileIndex, chunkIndex)`), `ContentKeyWrap` (X25519 ECDH + HKDF-SHA256 + ChaCha20-Poly1305 wrap/unwrap of the content key for the `JOIN_REQUEST`/`KEY_GRANT` handshake), `EncryptedChunkHasher` (Merkle leaf hashes over ciphertext).
- **`Manifest`**: `TransferManifest`/`ManifestCodec` now carry the sender's X25519 public key inside the signed payload — swapping it invalidates the Ed25519 signature, closing a MITM path.
- **`Protocol`**: new `JoinRequestMessage`/`KeyGrantMessage` wire messages + codec support. `SenderSession` generates the per-transfer content key (injected before the session starts, since the ciphertext Merkle root must exist before the manifest is signed), encrypts every chunk, and answers `JOIN_REQUEST` with `KEY_GRANT`. `ReceiverSession` generates its own X25519 keypair, sends `JOIN_REQUEST` only after independently trusting the signed manifest (TOFU check happens first — unchanged from M1), verifies the ciphertext Merkle proof, then decrypts; a repair-relaying receiver still only caches the verified `(ciphertext, proof)` pair, same design as M1, one layer later.
- Everything else — path safety, TOFU trust store, Ed25519 manifest signing, `IPeerTable`/`RepairCoordinator`, the transport layer — is untouched. Confirmed by `git diff --stat`: the entire change surface is `src/Castr.Core` (`Manifest/`, `Protocol/`, new `Security/` files) and its two test projects; no CLI/TUI/GUI/mobile code touched.

## Deliberate deviations from the design docs (all reviewed and accepted by QA)

1. **`JOIN_REQUEST`/`KEY_GRANT` travel over the shared multicast channel**, not a separate unicast socket as the original wording in [[wire-protocol]] implied. This matches the MVP trim M1 already applied to `CHUNK_REQUEST`/`CHUNK_RESPONSE` (see [[m1-core-summary]]) and keeps sessions on `IMulticastTransport` only, honoring the "no direct socket calls in session state machines" rule. No confidentiality is lost: `KEY_GRANT` is cryptographically readable only by its addressed receiver (bound to the receiver's ID and X25519 key in the AEAD construction) — QA confirmed a second on-segment receiver cannot unwrap another receiver's grant even by substituting its own receiver ID.
2. **The content key is generated outside `SenderSession` and injected**, not created in its constructor, because the ciphertext Merkle root has to exist before the manifest is signed — key generation is necessarily a step in transfer setup, before the session runs.
3. **A `JOIN_REQUEST` retry** was added, reusing the existing repair timer, so a lost `KEY_GRANT` doesn't stall a receiver forever under packet loss. `HandleKeyGrantAsync` is idempotent (returns early once the content key is already set), so duplicate grants from a retried request don't cause double-import or leak anything.

## QA review

An independent QA subagent rebuilt and re-ran the full suite itself (matched the claimed 186+4, zero failures) and went further than reading the code: captured real `CHUNK_DATA` off an eavesdropper transport and proved the payload is genuine ciphertext (not just labeled as such); flipped a ciphertext byte in flight and confirmed AEAD rejection + repair recovery; decrypted one chunk's ciphertext under another chunk's or another session's AAD and confirmed rejection; confirmed the nonce construction folds in `fileIndex` so `(file0, chunk0)` and `(file1, chunk0)` never collide, and that a fresh content key per transfer rules out cross-transfer nonce reuse regardless of session ID; confirmed a manifest with a swapped X25519 key fails signature verification (MITM-proof); and confirmed an untrusted sender's receiver never reaches the `JOIN_REQUEST` step at all, i.e. the new handshake didn't introduce a way to bypass TOFU. Verdict: **PASS**, no defects found, ships as-is. Two non-blocking hardening notes were logged, not treated as blockers:

## Non-blocking hardening notes (carried forward, not required for M1.5 to ship)

- `Castr.Core` doesn't currently enforce session-ID randomness/uniqueness itself (that's the caller's job — M1's `SenderSession` already required a caller-supplied session ID). Chunk encryption doesn't depend on session-ID uniqueness, but `ContentKeyWrap`'s HKDF salt does: a caller that reused a session ID across two transfers between the same sender/receiver pair would risk wrap-key reuse (the raw X25519 ECDH secret between a fixed pair is stable across transfers by construction). Worth adding a validation/assert when M2 wires up real session-ID generation, so this stays a documented caller contract rather than a silent trap.
- The unwrapped/exported content-key `byte[]` in `SenderSession.HandleJoinRequestAsync`/`ReceiverSession.HandleKeyGrantAsync` isn't zeroed after use — minor hygiene, consistent with how key material is already handled elsewhere in the M1 code, not a new gap this milestone introduced.
