## [2026-07-25] ingest | Post-M6 throughput investigation (analysis only, no code changed) + new performance-methodology documentation. A user field report after M6 shipped ("~8 MB/s now, but it bursts then stalls") reopened the throughput question: M6 raised the *average* ~5x but every M6 number was an average over a whole transfer, which cannot distinguish steady throughput from bursts plus multi-second stalls — consistency was never stated as a goal or measured. Spun up three parallel agents (systems-design analysis, a UFTP reference contrast, and an empirical instrumentation run in an isolated worktree). Two have reported and converged on the same primary cause, with every finding re-verified first-hand against the code before being recorded. **Primary finding (P0): a self-inflicted repair storm.** The 250 ms repair poll fires 250 ms into the transfer and requests *every* not-yet-arrived chunk with no cap and no awareness of carousel progress; the sender re-reads, re-encrypts, re-proofs and re-sends all of them concurrently with the still-running carousel, roughly doubling wire bytes and sender CPU — and because `_pending` is marked before the request is sent while `RepairOptions.RequestTimeout` is 5 s, a single lost request fragment costs 5 s of silence, so the real stall quantum is ~5 s not 250 ms. **P1: `PEER_HAVE` is quadratic** — the full bitmap is broadcast on every verified chunk as an awaited send inside `_stateGate`, totalling `FileSize²/(8·chunkSize²)` (13.6 MB for 80 MiB at 8 KB chunks; ~1.31 GB for 800 MiB, exceeding the payload). This cost was already present in M6's own chunk-8192→60000 measurement and was misattributed to datagram count at the time. **P2: the sender receives and decodes its own entire multicast transmission** (no own-echo filter, unlike the receiver), starving its own socket buffer and inbox so the kernel drops real control traffic — a ~5-line fix. Plus P3 (`_stateGate` taken per datagram holding disk+socket I/O), P4 (`ChunkPacketizer` wastes 39% of every non-zero packet; `maxDatagramPayloadBytes` exposed by no CLI/GUI surface), P5 (`CastrPaths.DefaultChunkSize = 8192` contradicts the documented 256 KB–1 MB range in the same file that cites it), P6 (`_chunkCache` never evicts — ~100 MB live set and ~143k small objects per 80 MiB transfer, causing gen2 pauses mid-transfer). **Explicitly rejected with reasons:** porting UFTP's TFMCC (reading UFTP's source shows its default rate is 1000 Kbps — *slower* than Castr — and its wire-speed mode is unpaced exactly like Castr, so congestion control is not the source of its advantage) and adopting UFTP's group-HMAC integrity model (Castr's Merkle-over-ciphertext is precisely what makes untrusted-peer repair safe and is load-bearing for the swarm/mobile tier).
