## [2026-07-25] ingest | Post-M6 throughput investigation (analysis only, no code changed) + new performance-methodology documentation. A user field report after M6 shipped ("~8 MB/s now, but it bursts then stalls") reopened the throughput question: M6 raised the *average* ~5x but every M6 number was an average over a whole transfer, which cannot distinguish steady throughput from bursts plus multi-second stalls — consistency was never stated as a goal or measured. Spun up three parallel agents (systems-design analysis, a UFTP reference contrast, and an empirical instrumentation run in an isolated worktree). Two have reported and converged on the same primary cause, with every finding re-verified first-hand against the code before being recorded. **Primary finding (P0): a self-inflicted repair storm.** The 250 ms repair poll fires 250 ms into the transfer and requests *every* not-yet-arrived chunk with no cap and no awareness of carousel progress; the sender re-reads, re-encrypts, re-proofs and re-sends all of them concurrently with the still-running carousel, roughly doubling wire bytes and sender CPU — and because `_pending` is marked before the request is sent while `RepairOptions.RequestTimeout` is 5 s, a single lost request fragment costs 5 s of silence, so the real stall quantum is ~5 s not 250 ms. **P1: `PEER_HAVE` is quadratic** — the full bitmap is broadcast on every verified chunk as an awaited send inside `_stateGate`, totalling `FileSize²/(8·chunkSize²)` (13.6 MB for 80 MiB at 8 KB chunks; ~1.31 GB for 800 MiB, exceeding the payload). This cost was already present in M6's own chunk-8192→60000 measurement and was misattributed to datagram count at the time. **P2: the sender receives and decodes its own entire multicast transmission** (no own-echo filter, unlike the receiver), starving its own socket buffer and inbox so the kernel drops real control traffic — a ~5-line fix. Plus P3 (`_stateGate` taken per datagram holding disk+socket I/O), P4 (`ChunkPacketizer` wastes 39% of every non-zero packet; `maxDatagramPayloadBytes` exposed by no CLI/GUI surface), P5 (`CastrPaths.DefaultChunkSize = 8192` contradicts the documented 256 KB–1 MB range in the same file that cites it), P6 (`_chunkCache` never evicts — ~100 MB live set and ~143k small objects per 80 MiB transfer, causing gen2 pauses mid-transfer). **Explicitly rejected with reasons:** porting UFTP's TFMCC (reading UFTP's source shows its default rate is 1000 Kbps — *slower* than Castr — and its wire-speed mode is unpaced exactly like Castr, so congestion control is not the source of its advantage) and adopting UFTP's group-HMAC integrity model (Castr's Merkle-over-ciphertext is precisely what makes untrusted-peer repair safe and is load-bearing for the swarm/mobile tier). Idea: replace the `CarouselIdleThreshold` heuristic with an explicit sender-emitted section-completion message, so a receiver *learns* that a chunk has been transmitted rather than inferring it from a timeout. Written up rather than implemented because this area has produced two liveness defects two rounds apart, and both were **design** errors that survived code review precisely because the design was never written down separately from the code — so the design gets contested first this time. The page leads with what the proposal is **not**: it is not a throughput change. The storm M7 fixed is gone (duplicate chunk datagrams 120,060 → 324; wire amplification 2.39× → 1.13× → **1.05× after M8**, against a 1.00× theoretical floor), so at most ~5% of wire traffic remains to remove, the measured bottleneck is per-datagram cost (~32 µs each way, `SendToAsync` alone 66% of sender CPU) rather than wire volume, and the M7 campaign measured deferring repair *in isolation* at **−11%** because the redundant repair stream was inadvertently supplying the sender's only send-path parallelism at `DefaultSendWindowSize = 1`. The actual motivation is deleting a bug class: both M7 defects reduce to one conflation — **at seed time, "never reached" and "finished" are indistinguishable, and the code treated them identically** (round 1 hung when a global idle timer let multicast repair traffic mask a never-reached tail; round 2 over-requested when per-file timers were seeded optimistically for files whose carousel had not started). An explicit signal makes the two distinguishable by construction. Secondary benefits: deletes `CarouselIdleThreshold` (which both reviewers independently called arbitrary — it derives from nothing in the codebase), restores an independent amplification bound that M8 regressed (`MaxRequestsPerPass` no longer binds for any file under 268 MB, leaving the carousel watermark as the sole defense), and removes the documented imprecision that a sparse repair packet can lift the scalar watermark over a range the carousel never sent. Prior art is UFTP's three interlocking guards (NAK only at section boundaries, server discards status for the section it is currently sending, repair in a later pass) — with the standing correction that UFTP's advantage is feedback discipline, **not** congestion control (its default rate is 1000 Kbps, slower than Castr; its wire-speed mode is unpaced exactly like Castr). Design sketch records two wire-format facts worth not rediscovering: a **new message type is additively backward-compatible** (both `ReceiverSession.HandlePacketAsync` and `SenderSession.TryDecode` already swallow the `InvalidDataException` that `MessageCodec.Decode` throws on unknown tags; tags 1-15 in use, 16 free), but **appending a field to an existing message is not symmetric** — an old reader tolerates trailing bytes while a new reader hits end-of-span on an old message and throws, which also constrains any future `Target` field on `ChunkRequestMessage`. Also records why the intuitive "wait until the end of the transmission" variant is worse than sections *and* worse than what ships today: a receiver losing chunk 3 of 400 would sit through the entire carousel before being allowed to ask, and all repair would be pushed into a serialized tail after the sender has moved on — reintroducing deliberately the exact burst-then-stall shape the original field report complained about. Five open questions carried, the sharpest being whether sections re-incur the −11%, which must be measured **together with** the tracked window-matrix follow-up rather than separately.
